Read the workflow contract completely before acting and follow it exactly.

Credentials come only from the inherited environment:
  - IMO_SOLVER_API_URL
  - IMO_SOLVER_TOKEN
  - IMO_SOLVER_MODEL
Never print, persist, or put the token on a command line.

Formal verification policy for this run:
  - Keep the formal gate required with `--lean-mode required`; local Lean
    runs first.
  - Enable AXLE only as fallback with `--axle-mode fallback`.
  - Use the matching hosted environment with

If `AXLE_API_KEY` or the AXLE client is unavailable, stop and report that
before launch; do not silently disable AXLE or weaken the formal gate.

Launch the orchestrator directly via exec_command (NOT screen). The process
runs as a child of the Codex app-server. Let the orchestrator read its model
configuration from the inherited environment. Redirect stdout and stderr
to files in the run directory. The exec_command call returns a session_id -
save it for monitoring with write_stdin.

After launch, wait 30 seconds and check:
  1. cat <run-dir>/progress.log - one line per state transition or error
  2. tail <run-dir>/stderr.log - API call failures and tracebacks
If progress.log shows any ERROR line, the run is failing. Do not keep
waiting; diagnose and fix before retrying. Do NOT poll for sentinel files.

Monitor the orchestrator using write_stdin with the session_id (empty chars,
yield_time_ms=300000) to detect completion, and separate exec_command calls
to check tail -5 progress.log and cat state.json. Poll no more than once
every 5 minutes. Only report when an iteration completes or an error occurs.

subdirectory and report substantively:
  - cat <run-dir>/run_XX/classify_YY.md — the verifier's derived machine verdict
  - cat <run-dir>/run_XX/verify_YY.json — audit, candidate hash, and frozen

  - head -30 <run-dir>/run_XX/verify_YY.md — key audit findings

    the exact statement reviewed before proof generation, when present

    including local Lean and AXLE PASS/FAIL/SKIP status
Summarize what the verifier found (critical errors, justification gaps) and
its final `VERDICT: yes|improve|no`. State whether the formalization passed and
whether the verifier judged `imo_problem` faithful to the original problem.
Do not just report token counts — explain what happened mathematically and what
the next step is trying to fix. Keep the summary concise but substantive.

The orchestrator has built-in protections that work without agent
intervention: a wall-clock timeout (threading.Timer, 5400s per API call) that
preserves partial reasoning/output for a bounded continuation, infrastructure
error backoff that retries the same outer run, an atomic per-output lock,
sandboxed generated-code execution, fail-closed machine verdicts, exact
candidate- and frozen-statement-hash tracking, and a pivot after 3 critical
failures. The acceptance sequence is proof_logic -> LEAN_STATEMENT ->
statement_fidelity -> freeze exact prefix -> LEAN_FORMALIZE/local Lean/AXLE ->
computation. A rejected statement is redrafted without mutating the informal
proof; proof generation and repair may not alter a frozen prefix.
Do not interfere with these mechanisms.

This must be a fresh, independent run. Do not read prior solutions, run
logs, verification reports, scratch work, or artifacts. The Desktop parent
is an orchestrator only and may not solve or grade the mathematics. Keep
the Goal active until the background workflow either persists a candidate
that passes all three distinct audits on one unchanged candidate SHA-256 and
one unchanged frozen-statement SHA-256, and passes the configured
formal-verification gate, or records a legitimate terminal failure.

Do not interpret a UI wait timeout as a stream failure, do not silently
duplicate active requests (this means YOUR session's own requests only -
another session running the same problem is not duplication), and do not
lower the acceptance threshold.
